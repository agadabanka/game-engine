Studio IDE — Design Doc

An AI-first cockpit for one game. Stay in the AI-first world; drop down to the knobs only when you want fine-grain control over a small part of a larger blueprint.

Engine repo: agadabanka/game-engine · Epic: #53 · Tracks issues #54–#63 · 2026-06-15

1. Why this exists

Today the only thing a human can author by hand on a shipped game is a free-text note.

The pipeline (tools/lib/pipeline.mjs, 4 phases / 19 stages / 72 substeps) turns a one-line concept into a finished game, written almost entirely by AI agents. Around the result we have:

  • The hub (hub/public/index.html) — read-only “look across / look inside” every game.
  • Per-game views — build.html (level select), design.html (the lens), diary.html. All read-only.
  • The one write gesture — in-game ⏸ → 📝 NOTE (Studio.Shell.note → POST /api/notes), which auto-files a GitHub issue and captures level, x, kind, and a screenshot.

So the owner can describe a change (a note) and wait for the whole pipeline, or hand-edit raw files / run CLIs. There is no place to sit inside one game and turn a specific knob with the AI beside you. The Studio IDE is that place — the missing middle.

2. The vision & principles

Keep the workflow AI-first: play the game, leave notes to improve it. When you want fine-grain control, drop down into the IDE — still an AI-first world, but focused on a smaller part of a larger blueprint. There you suggest an edit with the tool’s knobs and a Gemini prompt; that suggestion becomes a note, and the note is handled by the same notes→issues→fixes loop that handles every other note. Humans suggest; the AI handles.

The note is the single unit of work — on both ends. The IDE does not bypass the loop; it is a high-fidelity note composer. A note can be casual (in-game free text) or precise (composed in a tool: exact scope + knob deltas + a Gemini-ready prompt + a reference image + a previewed candidate). Either way it is submitted the same way and handled the same way. The IDE raises the fidelity of a suggestion; it never changes who applies it.
PrincipleWhat it means in the UI

5. The tool catalog

One tool per editable part of the game. Each composes a suggestion the same way; they differ only in artifact, knobs, and the gate handling runs. In every tool the output is a structured note — the “AI verb” below is what the owner suggests; the loop handles it.

Build order: Art is the first concrete tool (#64–#69, easiest to swap in/out); Levels (#62) proves the data-edit round-trip; Feel/Music/Identity (#63) follow.

Art editing model — every edit is a Gemini call. Recolor a character, redraw a sprite sheet, shift a world’s palette, swap a tile or prop — each is a Gemini nano-banana-pro (gemini-3-pro-image) generation. To edit an existing asset we pass it back as a reference image (generateImage(prompt, { refs }), already supported) so the model stays on-model and changes only what was asked — image-to-image editing. The knobs compose the edit instruction; the agent prompt bar is free-text. Gemini is required for the Art tool: without GEMINI_SA_JSON the tool is unavailable and says so — there is no procedural “tint” shortcut.

6. The round-trip — suggest → handle

Every tool works the same way. Steps 1–4 are the owner composing & previewing a suggestion in the IDE; step 5 submits it as a note; step 6 is the same notes loop handling it — the part that actually writes the game. This is the contract the whole IDE is built around.

#StepWhoMechanism
1Read the artifact, scoped to the selected elementIDEgame /api/meta or the repo file (levels.js, characters.js…)
2Edit via AI prompt or knobs — both compose the same structured proposalowneragent (NL → proposal) ↔ inspector (knobs → proposal)
3Preview live, scoped (for art, a Gemini-rendered candidate)IDEembedded game at ?level=N&char=key + Studio.Autopilot · nano-banana-pro
4Pre-check the gate so you preview a green suggestionIDEeval.mjs / validate-sprites.mjs / parity.mjs / fun-max.mjs
5Suggest — submit the proposal as a structured note (+ pinned scope, prompt, ref/candidate)ownerPOST /api/notes (enriched) → a GitHub issue, like any note
6Handle — the notes loop applies the proposal · re-gates (authoritative) · commits to the branch · appends the diary · closes the note + issueAI loopartifact write (POST /api/<artifact> / generator) + GitHub MCP commit + DELETE /api/notes

The gate runs twice on purpose: a fast pre-check in the IDE (so you don’t submit a broken suggestion) and the authoritative gate during handling (truth beats self-report). Handling can pick up a structured note immediately, so a suggestion can feel instant while still flowing through the one loop.

7. The flow — one note, two fidelities

This is the heart of the design: every path is a note that the same loop handles. The IDE just lets you author a more precise one.

  1. Play the live game (the AI-first world). A gap keeps killing you → ⏸ → 📝 note: “this gap before the goal feels unfair.” (Works today; captures level:3, x, screenshot.)
  2. The note lands on the blueprint, auto-routed by its metadata: level → Levels node, kind:art → Art node. The node lights up: “Levels ● 1 note.”
  3. The AI takes a first pass automatically — it drafts a candidate fix on the note. The board reads “Level 3 · 1 proposed fix.”
  4. If the AI’s pass is enough → Accept from the board. The loop handles it; the note closes. Never opened the IDE. Casual fidelity. ✓
  5. If you want control → “Open in IDE.” You drop into the Levels tool, scoped to Level 3, note pinned at its x, the AI’s draft pre-loaded, knobs live. A small part of the larger blueprint, still AI-first.
  6. Nudge the gap knob or re-prompt → preview the autopilot clear it → the 0-death pre-check goes green → Suggest edit. Your refined proposal is submitted as a precise note (scope + knob deltas + prompt + candidate) on the same note/issue.
  7. The notes loop handles it — applies the proposal, re-gates (authoritative), commits to the branch, writes the diary, closes the note + issue; the blueprint node goes green. Precise fidelity — same loop.

8. The /api surface

The IDE reads what already exists, submits through the existing notes endpoint (enriched), and the handler uses a small set of authenticated artifact-write endpoints. The split is the point: the IDE never writes the game directly — it submits a note; the loop writes.

Reads (exist today)

GET /api/meta     game identity + stages (drives the blueprint + Identity tool)
GET /api/diary    the build diary (markdown)
GET /api/notes    open/closed notes (now also carrying a structured proposal)
GET /api/config   engine/renderer info

Submit — what a tool produces (the IDE’s only write)

POST /api/notes   a note, casual OR structured. New optional fields:
  { text, level, x, kind, shot,            // (today) casual note
    tool,            // "levels" | "art" | "feel" | …  (routes to a tool)
    scope,           // { level } | { char } | { world } | { tile } | { prop }
    proposal,        // the structured edit object (knob deltas / field changes)
    prompt,          // the Gemini-ready instruction (art)
    ref, candidate } // reference image + previewed candidate (art)
  → becomes a GitHub issue, exactly like any note

Handle — what the notes loop uses to apply a note (authenticated)

POST   /api/levels      x-admin-token  → validate + write src/game/levels.js
POST   /api/characters  x-admin-token  → validate + write src/game/characters.js
POST   /api/meta        x-admin-token  → merge + write GAME_META.json
            (art/music notes → run tools/art*.mjs / music.mjs generators)
DELETE /api/notes?id=   x-admin-token  → close a handled note   (exists today)

Handling re-gates, then persists the artifact, commits to the claude/… branch (GitHub MCP), appends the diary, and closes the note + issue — the same path a casual note already follows, just driven by the note’s proposal instead of inferred from free text.

9. Architecture & data flow

  SUGGEST (the IDE) ──────────────────────┐        HANDLE (the notes loop) ───────────┐
  hub (/ide) ─reads→ game /api/{meta,        │        issue picked up ─→ apply proposal:  │
             notes,diary} → Blueprint/Stage  │          POST /api/<artifact> (authed)     │
  agent ─proposes→ proposal  ⟷  knobs        │          / run art*.mjs · music.mjs        │
            (same object)                     │        ─→ re-gate (authoritative)          │
  pre-check gate (fast)                       │        ─→ GitHub MCP commit to claude/…    │
  Suggest ─→ POST /api/notes {…, proposal} ──→ issue ─→ DIARY.md append                    │
                                              │        ─→ DELETE /api/notes (close)         │
                                              │        ─→ refreshed blueprint node          │
                                              └───────────────────────────────────────────┘

The proposal is the spine, carried inside the note: the agent and the knobs both produce it, the diff renders it, the pre-check validates the artifact it would produce, and handling applies it. Putting the proposal on the note is what unifies casual and precise suggestions — both are notes, both are handled by one loop, and a precise one simply carries an explicit proposal instead of being inferred from free text.
